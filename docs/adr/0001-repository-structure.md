# 0001. リポジトリ構成

- ステータス: 承認
- 日付: 2026-10-01
- 決定者: Yusuke Seki

## 背景

pactly は Next.js(フロントエンド)と NestJS(バックエンド)を独立したサービスとして構築する。API 契約は OpenAPI 定義を単一の真実源とし、`@nestjs/swagger` → `openapi-typescript` → `openapi-fetch` の流れで型をフロントエンドに渡す。

2つのサービスのコードをどう配置するかによって、次のことが決まる。

- OpenAPI から生成した型をフロントエンドへ渡す方法と、API 変更がフロントエンドに届くまでの手順
- CI/CD の構成(テスト対象の絞り込み、サービスごとのデプロイ)
- パッケージマネージャ、Lint/Format 設定、Renovate の管理単位

前提として、開発者は1人、目的は「設計判断を説明できる実績」であり、インフラは AWS のシンプル構成(App Runner または ECS Fargate)とする。

## 検討した選択肢

### A. pnpm workspaces によるモノレポ

```
pactly/
├── apps/
│   ├── web/            # Next.js
│   └── api/            # NestJS
└── packages/
    ├── api-client/     # openapi-typescript の生成型 + openapi-fetch クライアント
    └── config/         # ESLint / tsconfig / Prettier の共有設定
```

- 良い点
  - API の変更、型の再生成、フロントエンドの修正を**1つの PR にまとめられる**。CI で「生成した型に差分がないか」を検査すれば、契約のズレをマージ前に止められる
  - Lint・tsconfig・Renovate・CI の設定が1か所にまとまる
  - pnpm の厳格な依存解決により、宣言していない依存(phantom dependency)を防げる
  - ビルドが遅くなってきたら Turborepo を後から追加できる
- 悪い点
  - サービスごとに Docker イメージを作る際、workspace の依存を切り出す手間がかかる(`pnpm deploy` 等)
  - CI で「変更のあったアプリだけをテスト・デプロイする」ためにパスフィルタの設計が要る

### B. Nx によるモノレポ

- 良い点
  - NestJS と Next.js の公式プラグインがあり、雛形生成・影響範囲の解析・キャッシュが最初から揃う
  - `nx affected` で変更の影響を受けるプロジェクトだけを CI で動かせる
- 悪い点
  - Nx 独自の設定や実行モデルを覚える必要があり、ツールがやっていることを自分で説明しにくくなる
  - フレームワーク標準の CLI(`nest`、`next`)から離れた構成になり、アップデートで Nx の対応を待つことがある

### C. 2リポジトリ(web / api を分離)

- 良い点
  - サービスの独立性が最も明確。権限・CI・デプロイが完全に分かれる
  - 各リポジトリはフレームワーク標準の構成のまま使える
- 悪い点
  - 型を渡すには、npm パッケージ(GitHub Packages 等)として公開してバージョン管理するか、公開された OpenAPI 定義を web 側で取り込んで生成する必要がある
  - API の変更に**2つの PR と公開手順**が必要になり、1人開発では手間が大きい
  - Lint 設定や Renovate などを2か所で維持する必要がある

## 比較

| 観点 | A. pnpm モノレポ | B. Nx | C. 2リポジトリ |
| --- | --- | --- | --- |
| OpenAPI の型の受け渡し | ◎ workspace 参照 | ◎ workspace 参照 | △ パッケージ公開 or 取り込み |
| API 変更の手間 | ◎ 1 PR | ◎ 1 PR | △ 2 PR + 公開 |
| 導入・学習コスト | ○ | △ | ◎ |
| ツールの挙動を説明しやすいか | ◎ | △ | ◎ |
| サービスの独立デプロイ | ○ 要パスフィルタ | ◎ affected | ◎ |
| 1人開発との相性 | ◎ | ○ | △ |

## 決定

A. pnpm workspaces によるモノレポを採用する

### 理由

- フロントエンドもバックエンドも共通してTypeScriptで実装するから、リンターやフォーマッター、テスト系のライブラリの管理がしやすい
  - Cのリポジトリを分ける方法でも共通の設定パッケージを配布すればできるが、パッケージの公開やバージョン管理をしなくても1か所で共通化できるためAを選択した
- 機能ごとの実装に関して、場合によってはフロントエンド、バックエンドの実装や修正をひとつのPRにまとめられる
- API を変えたら、型の再生成とフロントの修正まで同じ PR に入り、CI で型の差分を検査して契約のズレをマージ前に止められる

### トレードオフ

- サービスごとに Docker イメージを作る際、workspace の依存を切り出す手間がかかる(`pnpm deploy` 等)
- CI で「変更のあったアプリだけをテスト・デプロイする」ためにパスフィルタの設計が要る
- サービスの独立性の明確さが損なわれ、運用での規律頼みになる

### トレードオフの対処策

- 学習も含めて workspaces の依存の切り出しや、デプロイのためのパスフィルタ設計もやってみる
- 個人開発なので、webとapiの間で直接的なimportをしないなどルールを設けて管理することで問題なく運用できる
  - apps/web の package.json に apps/api を書かなければエラーで検知できる
  - また、ESLint の no-restricted-imports(または dependency-cruiser)で禁止し、CI で落とすこともできる
